## Disco-RAG 项目简介
传统 RAG 普遍将检索得到的文本段落直接作为碎片化信息输入大模型，抹平了段落内部主次结构与段落之间逻辑关联，让模型只能接收杂乱无序的混合信息，无法获取条理化的参考资料。

传统 RAG 存在两大核心短板：一是无法识别段落内部语义层级，难以区分结论与前提条件；二是缺失段落间关联推理能力，无法判断多篇文献观点是相互支撑还是存在冲突。本质上，传统 RAG 的瓶颈不在于检索召回能力，而在于检索到内容却无法深度理解与结构化梳理。
针对以上问题，参考 https://arxiv.org/abs/2601.04377 提出的 Disco-RAG进行个人进行实验，在传统 RAG 的检索与生成回答之间新增语义读懂与逻辑梳理中间环节，构建全新的增强检索生成框架。


### 核心架构（三步走）

| 步骤       | 模块                                           | 功能                                                         |
| ---------- | ---------------------------------------------- | ------------------------------------------------------------ |
| **Step 1** | `rst_parser.py`                                | 给每个段落画一棵"论证树"——将段落拆解为最小语义单元(EDU)，标记核心/辅助，识别修辞关系（因果、对比、条件等） |
| **Step 2** | `relation_net.py`                              | 给所有段落织一张"关系网"——两两配对分析，预测支持/反驳/补充/限定等关系，构建有向关系图，识别冲突 |
| **Step 3** | `outline_generator.py` + `answer_generator.py` | 先列提纲，再写答案——基于论证树和关系网生成写作提纲，再按提纲引导模型产出结构化回答 |

### 使用方法

**1. 配置LLM（必须）**
```bash
# 支持任何OpenAI兼容API
export DISCO_RAG_API_BASE="https://open.bigmodel.cn/api/paas/v4"
export DISCO_RAG_API_KEY="your-api-key"
export DISCO_RAG_MODEL="glm-4-flash"
```

**2. 命令行运行**
```bash
# 运行维生素D演示
python3 -m disco_rag --demo

# 自定义提问
python3 -m disco_rag -q "你的问题" -p para1.txt para2.txt

# 使用文档库
python3 -m disco_rag -q "你的问题" --corpus docs.json
```

**3. Python代码调用**
```python
from disco_rag.llm_client import LLMConfig
from disco_rag.pipeline import DiscoRAGPipeline

config = LLMConfig(api_key="your-key", model_name="glm-4-flash")
pipeline = DiscoRAGPipeline(llm_config=config)

# 一行代码运行
answer = pipeline.ask(
    "补充维生素D能预防流感吗？",
    paragraphs=[
        "在冬季维生素D水平偏低的成年人群中...",
        "大规模随机对照试验未发现...",
    ],
)
```

**4. 逐步调用各模块**
```python
from disco_rag.rst_parser import RSTParser
from disco_rag.relation_net import RelationNetBuilder
from disco_rag.outline_generator import OutlineGenerator
from disco_rag.answer_generator import AnswerGenerator

# Step 1: 论证树
trees = RSTParser(llm).parse_paragraphs([("P1", "段落1"), ("P2", "段落2")])

# Step 2: 关系网
net = RelationNetBuilder(llm).build(trees)

# Step 3: 提纲 + 答案
outline = OutlineGenerator(llm).generate(question, trees, net)
answer = AnswerGenerator(llm).generate(question, outline, trees, net)
```

### 设计亮点

- **零训练**：全程基于LLM Prompt工程，不需要任何训练或微调
- **可插拔LLM**：支持任何OpenAI兼容API（智谱、OpenAI、vLLM、Ollama等）
- **完整可追溯**：每步中间结果（论证树、关系网、提纲）都可查看和保存
- **对比传统RAG**：自动生成传统RAG答案用于效果对比
- **灵活使用**：支持CLI、Pipeline一键运行、逐步模块调用三种模式

## 一、整体架构回顾

Disco-RAG 的核心创新是在"搜"和"答"之间插入一个**"读懂"环节**，三步走：

```
用户问题 → 检索段落 → [Step1 论证树] → [Step2 关系网] → [Step3 提纲+答案]
                         ↑                    ↑                    ↑
                    "段落内部读懂"       "段落之间读懂"        "读懂后再写"
```

下面逐个模块深入剖析。

---

## 二、模块详解

### 📦 模块1：`llm_client.py` — LLM统一客户端

#### 作用
所有模块调用大模型的唯一入口。把API差异屏蔽在底层，上层模块只需调用 `chat()` 或 `chat_json()`。

#### 设计动机
Disco-RAG 的三个核心步骤都需要调用LLM做结构化分析，但不同用户可能使用不同的LLM服务（智谱、OpenAI、本地vLLM、Ollama等）。如果每个模块都各自管理API连接，代码会重复且难以维护。因此需要一个统一的客户端层。

#### 实现原理

```
┌─────────────────────────────────┐
│  上层模块 (RSTParser等)          │
│  调用 llm.chat() / llm.chat_json() │
└──────────────┬──────────────────┘
               │
┌──────────────▼──────────────────┐
│  LLMClient                      │
│  ┌─────────────────────────┐    │
│  │ chat(system, user, temp)│    │  ← 普通文本对话
│  │ chat_json(sys, user)    │    │  ← 要求返回JSON并自动解析
│  └─────────────────────────┘    │
│  ┌─────────────────────────┐    │
│  │ 主配置 → OpenAI Client  │    │  ← 优先使用
│  │ 备选配置 → Fallback     │    │  ← 主配置失败时降级
│  └─────────────────────────┘    │
└─────────────────────────────────┘
```

**关键实现细节：**

1. **OpenAI兼容协议**：几乎所有主流LLM服务都支持OpenAI的 `/v1/chat/completions` 接口格式，所以只需切换 `api_base` 就能对接不同服务。

2. **JSON解析的鲁棒性**：LLM输出JSON时常会"夹带私货"（包在markdown代码块里、前面加说明文字等），`_parse_json_response()` 做了三层兜底：
   - 先直接 `json.loads()`
   - 去除 ` ```json ``` ` 包裹后再试
   - 用 `{` 和 `}` 定位提取子串再试
   - 最后尝试 `[` `]` 数组提取

3. **降级机制**：主模型调用失败时，自动尝试备选配置（`fallback_api_base`），提高系统可用性。

### 📦 模块2：`rst_parser.py` — RST修辞结构解析器（论证树）

#### 作用
这是 Step 1 的核心。将每个段落拆解为最小语义单元（EDU），标注核心/辅助角色，识别修辞关系，构建**论证树**。

#### 核心概念

**EDU（Elementary Discourse Unit）**：语言学中最小的、不可再分的语义单元。例如：
```
"在冬季维生素D水平偏低的成年人群中，额外补充维生素D后流感发病率下降了12%。"
                     ↕ 拆分为两个EDU
EDU1（辅助）: "在冬季维生素D水平偏低的成年人群中"  ← 限定条件
EDU2（核心）: "额外补充维生素D后流感发病率下降了12%" ← 核心结论
```

**Nucleus（核心）vs Satellite（辅助）**：RST理论的核心区分——每段话都有一个"重心"，其他部分都是为这个重心服务的。传统RAG把整段话等权重投喂，模型分不清"12%下降"和"仅限特定人群"哪个才是重点。

**修辞关系**：EDU之间的逻辑连接方式。关键关系包括：

| 关系类型 | 含义 | 例子 |
|---------|------|------|
| `condition` | A是B成立的前提 | "如果年龄>60岁" → "风险增加" |
| `evidence` | A为B提供证据 | "RCT显示..." → "因此有效" |
| `contrast` | A与B形成对比 | "短期有效" vs "长期无效" |
| `concession` | 让步 | "虽然价格高" → "但质量好" |
| `elaboration` | 展开 | "三种方法" → "分别是..." |
| `cause/result` | 因果 | "因为下雨" → "所以延期" |

#### 实现原理

```
输入: 段落文本
         │
         ▼
┌─────────────────────┐
│ 构造Prompt           │  把段落文本 + RST分析要求
│ (系统提示+用户提示)   │  封装成结构化Prompt
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ 调用LLM              │  temperature=0.05（极低温度，
│ (chat_json)          │  确保结构化输出稳定）
└──────────┬──────────┘
           │
           ▼  LLM返回JSON:
           │  {
           │    "summary": "段落摘要",
           │    "edus": [
           │      {"edu_id":"E1", "role":"satellite", 
           │       "relation_to_parent":"condition", "parent_id":"E2"},
           │      {"edu_id":"E2", "role":"nucleus", ...}
           │    ],
           │    "root_id": "E2"
           │  }
           ▼
┌─────────────────────┐
│ _build_tree_from_response │  JSON → Python对象
│                       │  1. 创建EDU对象列表
│                       │  2. 建立parent-children关系
│                       │  3. 确定根节点
└──────────┬──────────┘
           │
           ▼
      RSTTree 对象
      ├── edus: [EDU, EDU, ...]
      ├── get_core_claim() → 核心论点
      ├── get_conditions() → 限定条件列表
      └── format_tree_visual() → 可视化输出
```

**关键方法的作用：**

- `get_core_claim()`：提取所有核心(Nucleus)EDU拼接，得到"这段话到底在说什么"
- `get_conditions()`：提取辅助(Satellite)EDU中关系为 condition/background/concession 的，得到"这段话的结论在什么条件下成立"
- `format_tree_visual()`：树形缩进打印，直观展示论证结构

**为什么用LLM而不是规则解析？** RST解析是典型的"理解"任务，需要语义判断。传统NLP的RST解析器（如两阶段CRF模型）准确率有限，且需要大量标注数据。利用LLM的零样本能力，通过精心设计的Prompt，可以高质量完成RST解析，且无需训练——这正是Disco-RAG"零训练"理念的体现。

### 📦 模块3：`relation_net.py` — 段落关系网络构建器

#### 作用
这是 Step 2 的核心。对所有检索到的段落做两两配对分析，预测它们之间的逻辑关系，构建一张**有向关系图**。

#### 核心概念

传统RAG把检索结果当"散装零件"，段落间的逻辑关系完全丢失。关系网络要解决的问题是：**这些段落之间到底是在互相支持、互相打脸、还是在各说各话？**

**六种段落间关系：**

| 关系 | 含义 | 典型场景 |
|------|------|---------|
| `support` | B支持A的结论 | 两项独立实验得出相同结论 |
| `contradict` | B与A立场冲突 | 观察性研究 vs RCT结论相反 |
| `supplement` | B补充A的信息 | A说效果，B说机制 |
| `elaborate` | B详细展开A | A给出结论，B给出详细数据 |
| `condition` | B为A提供限定 | A说有效，B说仅在特定条件下 |
| `neutral` | 无直接关联 | 讨论不同话题 |

#### 实现原理

```
输入: [RSTTree, RSTTree, ...] (所有段落的论证树)
              │
              ▼
┌─────────────────────────────┐
│  两两配对遍历                 │  对N个段落，共 N×(N-1) 对
│  for i, src in enumerate(): │  （有向图，A→B 和 B→A 分别分析）
│    for j, tgt in enumerate():│
│      if i == j: continue    │
└──────────────┬──────────────┘
               │
               ▼  对每一对 (src, tgt):
┌─────────────────────────────┐
│  构造分析Prompt               │
│  关键：不只传原文，还传入       │
│  ┌─────────────────────┐    │
│  │ • 段落原文            │    │  ← 原始信息
│  │ • 核心论点            │    │  ← 从RST树提取
│  │ • 限定条件            │    │  ← 从RST树提取
│  │ └─────────────────────┘    │
│  这样LLM能基于"读懂"的结构   │
│  做关系判断，而非只看表面文字  │
└──────────────┬──────────────┘
               │
               ▼
┌─────────────────────────────┐
│  LLM返回关系判断              │
│  {                           │
│    "relation_type": "contradict",
│    "confidence": 0.85,      │
│    "explanation": "...",    │
│    "conflict_point": "..."  │  ← 矛盾点的精确描述
│  }                           │
└──────────────┬──────────────┘
               │
               ▼
        RelationNet 有向图
        ├── paragraphs: {id: RSTTree}
        ├── edges: [ParagraphRelation, ...]
        ├── get_contradictions() → 所有冲突
        ├── has_conflict_between(p1, p2) → 是否矛盾
        └── format_net_visual() → 可视化
```

**为什么传入核心论点和限定条件？** 这是关系网络区别于简单"语义相似度"的关键。看维生素D的例子：

- 段落A的核心论点："发病率下降12%"，限定条件："冬季+偏低人群"
- 段落B的核心论点："未发现显著关联"，限定条件："无"

只看原文，LLM可能觉得"都是讲维生素D和流感"就判为"补充"；但看到限定条件的差异后，LLM能判断出"一个是有条件的正面结论，一个是整体性的否定结论"→ 这是**矛盾**而非补充。

**冲突点的精确描述**：`conflict_point` 字段是专门为后续提纲生成准备的。它不只是说"有矛盾"，而是精确描述矛盾在哪里（如"特定人群有效 vs 整体无效"），让提纲生成器能针对性地安排协调策略。

### 📦 模块4：`outline_generator.py` — 写作提纲生成器

#### 作用
这是 Step 3 前半部分。综合用户问题、论证树、关系网，生成一份**写作提纲**，指导模型"怎么写"而不是"写什么"。

#### 设计动机
传统RAG让模型直接从原始段落生成答案，模型面临"信息过载+结构缺失"的双重困境。提纲的作用是：**先把思路理清，再动笔写**——就像写作文先列提纲一样。

#### 实现原理

```
输入: question + rst_trees + relation_net
              │
              ▼
┌─────────────────────────────────────┐
│  三类信息汇聚                         │
│  ┌─────────────────────────────┐    │
│  │ 段落信息 (paragraphs_info)   │    │  每个段落的：
│  │  • 原文                      │    │   原文、摘要、核心论点、
│  │  • 核心论点 + 限定条件       │    │   限定条件、EDU结构
│  │  • EDU修辞结构               │    │
│  ├─────────────────────────────┤    │
│  │ 关系信息 (relations_info)    │    │  非中立的段落间关系：
│  │  • 支持/反驳/补充的边        │    │   谁→谁、什么关系、理由
│  │  • 置信度和说明              │    │
│  ├─────────────────────────────┤    │
│  │ 冲突信息 (conflicts_info)    │    │  专门整理矛盾：
│  │  • 冲突双方的核心论点        │    │   双方论点、冲突点、说明
│  │  • 精确的冲突点描述          │    │
│  └─────────────────────────────┘    │
└──────────────┬──────────────────────┘
               │
               ▼
┌──────────────────────────────────────┐
│  LLM生成提纲                          │
│  输出结构：                            │
│  ┌────────────────────────────────┐  │
│  │ overall_strategy:              │  │  整体写作策略
│  │   "先呈现各方证据，            │  │  （如何组织答案）
│  │    再协调矛盾，                │  │
│  │    给出有条件的判断"           │  │
│  ├────────────────────────────────┤  │
│  │ conflict_resolution:           │  │  矛盾协调方案
│  │   "从研究设计差异角度分析      │  │  （如何处理冲突）
│  │    矛盾原因"                  │  │
│  ├────────────────────────────────┤  │
│  │ conclusion_strategy:           │  │  结论策略
│  │   "基于证据给出层次化建议"     │  │  （如何收尾）
│  ├────────────────────────────────┤  │
│  │ sections: [                    │  │  章节规划
│  │   {                            │  │
│  │     title: "证据梳理",         │  │
│  │     content_plan: "...",       │  │  要写什么
│  │     evidence_ids: ["P1","P2"], │  │  引用哪些段落
│  │     strategy: "...",           │  │  怎么写
│  │     key_points: [...]          │  │  必须涵盖的要点
│  │   },                           │  │
│  │   ...                          │  │
│  │ ]                              │  │
│  └────────────────────────────────┘  │
└──────────────────────────────────────┘
```

**提纲 vs 直接生成的本质区别：**

| 维度 | 传统RAG直接生成 | Disco-RAG先提纲后生成 |
|------|----------------|---------------------|
| 信息组织 | 模型自行决定 | 提纲预先规划 |
| 矛盾处理 | 可能忽略或简单选边 | 提纲明确安排冲突分析章节 |
| 限定条件 | 常被遗漏 | 提纲的key_points强制涵盖 |
| 证据引用 | 可能凭"印象" | evidence_ids精确指定 |
| 结论风格 | 容易简单化 | conclusion_strategy约束有条件判断 |

### 📦 模块5：`answer_generator.py` — 最终答案生成器

#### 作用
Step 3 后半部分。按照提纲的指导，让模型产出最终的**结构化回答**。

#### 实现原理

```
输入: question + outline + rst_trees + relation_net
              │
              ▼
┌─────────────────────────────────────────┐
│  两部分信息注入                           │
│  ┌─────────────────────────────────┐    │
│  │ 提纲文本 (outline_text)          │    │  章节结构 + 策略 + 要点
│  │  → 告诉模型"怎么组织答案"        │    │
│  ├─────────────────────────────────┤    │
│  │ 证据文本 (evidence_text)         │    │  每个段落的：
│  │  → 告诉模型"可以引用什么"        │    │   原文、核心论点、
│  │                                │    │   限定条件、关系标注
│  │  特殊标注：                      │    │
│  │  ⚠️ 限定条件 → 强制注意          │    │
│  │  🔗 关系标注 → 关联上下文        │    │
│  └─────────────────────────────────┘    │
└──────────────┬──────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────┐
│  System Prompt 约束写作行为               │
│  ┌─────────────────────────────────┐    │
│  │ 1. 严格遵循提纲的章节结构        │    │  ← 不能自由发挥
│  │ 2. 引用证据要准确               │    │  ← 不能歪曲原文
│  │ 3. 限定条件必须明确标注          │    │  ← 不能遗漏前提
│  │ 4. 矛盾要客观呈现               │    │  ← 不能只选一边
│  │ 5. 结论要有条件判断              │    │  ← 不能简单是/否
│  └─────────────────────────────────┘    │
└──────────────┬──────────────────────────┘
               │
               ▼
          最终答案文本
```

**为什么分"提纲"和"答案"两步，而不是一步到位？** 这是核心设计决策：

1. **分工明确**：提纲负责"战略规划"（写什么、怎么组织），答案负责"战术执行"（具体措辞、逻辑衔接）。如果合为一步，模型容易在规划时就开始写内容，导致结构混乱。

2. **温度策略不同**：提纲需要高度结构化（temperature=0.1），答案需要自然流畅（temperature=0.3）。分开调用可以精确控制。

3. **可审查**：提纲是中间产物，用户可以先审查提纲是否合理，再决定是否继续生成答案。这在实际应用中非常有价值。

### 📦 模块6：`retriever.py` — 简易检索器

#### 作用
在"搜"这个环节提供基础能力。支持TF-IDF关键词检索和可选的语义向量检索。

#### 实现原理

```
┌──────────────────────────────────────────┐
│  SimpleRetriever                          │
│                                           │
│  ┌──────────────────────────────┐        │
│  │  Document文档库               │        │
│  │  [Document, Document, ...]   │        │
│  └──────────────┬───────────────┘        │
│                 │                         │
│        ┌───────▼───────┐                 │
│        │ search(query) │                 │
│        └───┬───────┬───┘                 │
│            │       │                      │
│   ┌────────▼┐  ┌───▼────────┐           │
│   │关键词检索│  │语义检索(可选)│           │
│   │ TF-IDF  │  │sentence-   │           │
│   │         │  │transformers│           │
│   └────┬───┘  └────┬───────┘           │
│        │           │                     │
│        └─────┬─────┘                     │
│              ▼                            │
│   [(Document, score), ...]               │
│    按相关度降序排列                        │
└──────────────────────────────────────────┘
```

**TF-IDF检索的实现：**

1. **建索引**：对每个文档分词（中文按字、英文按空格），统计每个词在多少文档中出现（文档频率DF）
2. **打分**：查询词在文档中出现 → `score += TF × IDF`，其中 `IDF = log((N+1)/(DF+1)) + 1`
3. **排序**：按得分降序返回 top_k

**为什么提供两种检索模式？** TF-IDF轻量无依赖，适合快速演示；语义检索更智能但需要安装 `sentence-transformers`。Disco-RAG 的核心创新在"读懂"环节而非"搜"环节，所以检索器用简单实现即可，生产环境建议替换为专业引擎。

### 📦 模块7：`pipeline.py` — 主流程编排

#### 作用
把上述所有模块串联成完整的 Disco-RAG 流程，提供一键运行和结果管理。

#### 实现原理

```
DiscoRAGPipeline.run(question, paragraphs, ...)
│
├── 1. 获取段落
│   ├── 如果传入paragraphs → 直接使用
│   └── 如果未传入 → retriever.search(question, top_k)
│
├── 2. Step 1: RST解析
│   └── rst_parser.parse_paragraphs([(pid, text), ...])
│       └── 对每个段落调用LLM → RSTTree列表
│
├── 3. Step 2: 关系网络
│   └── relation_builder.build(rst_trees)
│       └── 对每对段落调用LLM → RelationNet
│
├── 4. Step 3a: 生成提纲
│   └── outline_generator.generate(question, trees, net)
│       └── 调用LLM → Outline
│
├── 5. Step 3b: 生成答案
│   └── answer_generator.generate(question, outline, trees, net)
│       └── 调用LLM → 答案文本
│
├── 6. [可选] 对比传统RAG
│   └── _generate_traditional_rag(question, paragraphs)
│       └── 直接拼接段落 + 简单Prompt → 答案文本
│
└── 7. 返回 DiscoRAGResult
    ├── answer: Disco-RAG答案
    ├── traditional_answer: 传统RAG答案
    ├── rst_trees: 论证树
    ├── relation_net: 关系网
    ├── outline: 提纲
    ├── timing: 各阶段耗时
    ├── save_to_file() → JSON
    └── format_report() → 可读报告
```

**传统RAG对比方法的实现**：`_generate_traditional_rag()` 把所有段落简单拼接，用最基础的Prompt让模型回答。这模拟了大多数RAG系统的实际做法——不做任何结构分析，直接把检索结果丢给模型。对比结果能直观展示Disco-RAG在答案质量上的提升。

## 四、核心设计哲学总结

| 原则 | 体现 |
|------|------|
| **零训练** | 所有"理解"能力来自LLM + 精心设计的Prompt，无需标注数据或微调 |
| **读懂而非搜索** | 检索器是简易实现，核心创新在RST解析和关系网络 |
| **结构化中间产物** | 论证树、关系网、提纲都是可查看、可审查的结构化输出 |
| **分而治之** | 把"读懂文档"拆成段落内(RST)和段落间(关系网)两个独立子问题 |
| **提纲先行** | 先规划再执行，避免模型在信息过载时"胡说八道" |
| **有条件的判断** | 每一步都在强化"限定条件"的识别和保留，最终答案必然是有层次的 |
